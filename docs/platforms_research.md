# 国内量化平台期货 K 线聚合调研报告

> 调研目标：看 vnpy 等成熟框架怎么做期货 K 线合成、怎么处理休盘/午休/夜盘跨日，踩过哪些坑，
> 为自研 LuaJIT K 线库（1m base + roll-up 派生）提供参考，避免重复造轮子时翻车。
> 调研日期：2026-07-23

---

## 一、两大对齐流派（先看全局）

所有平台的分钟 K 线聚合，本质就两条路线：

| 流派 | 判定方式 | 代表 | 优点 | 缺点 |
|---|---|---|---|---|
| **墙上时钟对齐**（wall-clock） | `分钟数 % window == 0` | vnpy 原生、文华财经、多数看盘软件 | 简单、跨软件一致 | 需对休盘打补丁；**只能用能整除 60 的窗口**（2/3/5/6/10/15/20/30） |
| **交易时长/根数对齐**（session-relative） | 累计"已走过的交易分钟"/连续根数切窗口 | vnpy 社区 hxxjava 的 MyBarGenerator | 支持任意周期（90 分钟、4 小时）；天然跨休盘连续 | 实现复杂，需完整交易时段表 |

> 结论先行：**你已选的"时钟对齐 + 休盘强制封口 + 缺失不补空"正是 vnpy 原生走的路，而且是主流。**
> vnpy 原生的几个著名 bug，恰恰是"时钟对齐没配好休盘补丁"造成的——你已经想到封口，天然避开。
> 只有当你未来要做 90 分钟这类"不能整除 60"的周期时，才需要升级到交易时长对齐流派。

## 二、vnpy BarGenerator 源码级机制（核心）

代码位于 `vnpy/trader/utility.py`。它干两件事：tick→1m、1m→xm/xh/日线。

### 2.1 tick → 1 分钟 bar
- 判定新分钟：`self.bar.datetime.minute != tick.datetime.minute`（或 hour 不同）时，封口上一根 1m 并回调 `on_bar`。
- bar 时间戳取**起始时间**：`datetime.replace(second=0, microsecond=0)` → **左闭**标注。
- 脏 tick 过滤：`last_price == 0`（无效价）、`tick.datetime < last_tick.datetime`（时间倒退）直接丢弃。
- volume 用**差值**累加：`tick.volume - last_tick.volume`（因为 CTP 的 volume 是当日累计值，不是增量！）——**这是个关键细节，容易错**。
- open_interest 取最新时点值，不累加。

### 2.2 1 分钟 → X 分钟 bar
核心判定就一行（墙上时钟、左闭右开 `[0, window)`）：
```python
if self.interval == Interval.MINUTE:
    if not (bar.datetime.minute + 1) % self.window:
        finished = True   # 下一分钟正好跨窗口边界 → 当前根收尾
```
即"如果下一分钟正好是窗口整数倍，这一分钟就是最后一根"。所以 15m 用的是 `[0,15)` 的数据。
**window 必须能整除 60**，否则无法把 60 分钟均匀切片。

### 2.3 小时线 / 日线
- 小时线：`bar.datetime.minute == 59` 或 `bar.datetime.hour != hour_bar.datetime.hour` 触发。
- 日线（较新版本才支持）：判断 `bar.datetime.time() == 收盘时间`（如 14:59）触发封口；国债期货收盘 15:15 特殊处理。
- **日线夜盘归属**：合成逻辑会把夜盘时段并入**下一交易日**，日 K 开盘价 = 夜盘开盘价，符合交易所规则。（正好对应你之前问的 trading_day）

### 2.4 强制封口 `generate()`
提供 `generate()` 手动强制收尾当前未完成 bar——**收盘时必须调用**，否则最后一根 bar 因为没有"下一根"来触发而丢失。

## 三、vnpy 的已知坑（重点！都有据可查）

### 坑 1：休盘导致非常规周期（20 分钟）合成错误 ⭐
**现象**：20 分钟线本应在每小时 19/39/59 分封口。但 10:19 处于休盘（10:15–10:30 无数据），不触发切分，一路等到 10:39 才切，导致这根 K 线**错误地包含了 10:00–10:14 和 10:30–10:49 共 35 分钟**数据。
**官方解法**：对三大商品所（SHFE/DCE/CZCE）在收到 **10:14** 分钟数据时强制切分：
```python
elif bar.datetime.time() == time(10, 14) and bar.exchange in [SHFE, DCE, CZCE]:
    finished = True
```
**对我们的启示**：这就是"休盘边界强制封口"的实战版。我们的方案用 `in_session(t) 且 not in_session(t+1)` 通用判定，比硬编码 10:14 更干净、覆盖所有休盘/午休/收盘。
来源：https://zhuanlan.zhihu.com/p/352485736

### 坑 2：小时线多算一根分钟 bar（Issue #2775）⭐
**现象**：MINUTE 分支用 `(minute+1) % window`（左闭右开 `[0,60)`），但 HOUR 分支用 `bar.datetime.hour != last_bar.hour`（左开右闭 `(0,60]`），**两个分支边界语义不一致**，导致小时线多计一根分钟 bar。且午休 11:30→13:30 会把 13:30 的分钟错算进上一根小时线。
**启示**：边界语义（左闭右开 vs 左开右闭）**全库必须统一**。我们统一用左闭右开 `[start, end)`。
来源：https://github.com/vnpy/vnpy/issues/2775

### 坑 3：模拟交易无法合成 15/30 分钟线（Issue #1162）
指标初始化 + window bar 对齐在模拟盘环境下出问题，反映了"依赖 tick 推动"的脆弱性。
来源：https://github.com/vnpy/vnpy/issues/1162

### 坑 4：依赖 tick 推动封口（架构性）⭐
vnpy 的 bar 封口靠"下一根数据到来"触发。后果：
- 流动性差的合约某分钟无 tick → bar 延迟封口甚至缺失；
- 收盘最后一根必须靠 `generate()` 或外部定时器补封口，否则丢失；
- 郑商所曾有收盘无 tick 导致最后一根 bar 时间戳错误的问题（Issue #957）。
**启示**：我们的合成器应有**时段感知的主动封口**（到收盘/休盘边界就封口），而不是纯靠下一根 tick 推动。
来源：https://github.com/vnpy/vnpy/issues/957

### 坑 5：只支持整除 60 的窗口
原生无法做 90 分钟、4 小时等周期。想要就得改用交易时长对齐（见下）。

### 坑 6：多周期事件不触发（周线/日线）
社区反复出现"用 tick 合成周线/日线，回调不触发"的配置类问题，多因多周期链路（tick→1m→日→周）没串对。
来源：https://www.vnpy.com/forum/post/68069

## 四、社区最系统的方案：hxxjava 的 MyBarGenerator ⭐⭐

vnpy 社区帖《彻底解决 K 线生成器的问题——日内对齐等交易时长的 K 线生成器》给了目前最完整的思路，很值得借鉴：

**核心思想**：不用墙上时钟，改用**交易时段字符串驱动 + 等交易时长对齐**。
- 交易时段用一个字符串描述：`"21:00-23:00,09:00-10:15,10:30-11:30,13:30-15:00"`
- `TradingHours` 类负责：解析各段起止（天内秒）、判断某时间属于哪个交易日（处理夜盘归属、周一跨周末插 2 天）、算日内窗口索引。
- 关键：用**"已走过的交易时长 traded_t"**（跳过休市段的净交易秒数）去切窗口，而非墙上时钟。这样：
  - 天然**跨休盘连续**，无需对 10:14 打补丁；
  - 支持**任意周期**（90 分钟、4 小时=240 分钟）；
- 生成规则明确：
  - 日内 K 线：**对齐交易日开盘 + 等交易时长 + 忽略休市 + 不跨日、遇收市强制截止**；
  - 日 K：休市数据视为非法；收盘时间或收到超过收盘的数据时生成；
  - 周/月/年 K：由日 K 逐级合成，处理交易日历。
- **明确不处理长假**：作者说得很直白——"我们不是交易所，不知道各种节假日规定"，几乎所有软件都不处理跨长假对齐，这不影响使用。

**启示**：这套"交易时段字符串 + 交易时长对齐"正好对应我们设计稿里的 `calendar.lua` + `period.lua`。
如果你要支持 90 分钟这类周期，直接借鉴它的 traded_t 算法。
来源：https://www.vnpy.com/forum/topic/30193

## 五、其他平台对比

### TqSdk（天勤）——服务器端合成，另一条哲学 ⭐
- **K 线不在本地合成**，而是由天勤**行情网关服务器端生成并推送**（tick、各周期 K 线都是服务器给）。
- 好处：多合约 K 线**自动时间对齐**、休盘/夜盘/跨日**平台已处理好**、多端一致、本地零合成负担。
- 代价：依赖天勤服务器与账号；离线/自建数据源不适用。
- 对比：vnpy 是"本地接 tick 自己合成"，天勤是"服务器合成直接给"。你自研 LuaJIT 库属于 vnpy 这一派（本地合成），所以 vnpy 的坑对你更有参考价值。
- 来源：https://doc.shinnytech.com/tqsdk/latest/advanced/for_vnpy_user.html

### 掘金量化 / 聚宽 JoinQuant / 米筐 RiceQuant
- 这类**数据平台型**框架，多周期 bar 通常由平台数据服务预先合成好，用户按 `frequency`（如 '1m'/'5m'/'1d'）直接取，休盘/夜盘对齐由平台数据侧保证。
- 用户一般**不需要自己处理休盘边界**，但也就**看不到、控制不了**合成细节——想自定义非标周期时反而受限。
- （注：本节为平台通用认知，未逐一核到源码级细节；vnpy 部分是源码/issue 级确证。）

### backtrader（国外，作对比）
- 用 `resample`/`replay` 机制做周期转换，有 session 边界概念（`sessionstart`/`sessionend`），但**对中国期货的午休/夜盘跨日支持不友好**，需要自定义 `TradingCalendar` 和 filter，中文社区普遍反馈"直接用会错、要改"。

## 六、给自研 LuaJIT 库的最佳实践清单（结论）

结合以上，落到你的设计上：

1. ✅ **1m base + 时钟对齐 roll-up** —— 与 vnpy 原生、文华一致，主流稳妥。
2. ✅ **休盘/午休/收盘边界强制封口** —— 用 `in_session(t) 且 not in_session(t+1)` 通用判定，
   直接规避 vnpy 坑 1（20 分钟错误）和坑 4（收盘丢最后一根）。比 vnpy 硬编码 10:14 更干净。
3. ⚠️ **边界语义全库统一为左闭右开 `[start, end)`** —— 规避 vnpy 坑 2（小时线多算一根）。
4. ⚠️ **主动封口，不纯靠下一根推动** —— 合成器要有时段感知的定时/边界封口，规避坑 4。
5. ⚠️ **volume 用差值累加** —— CTP 的 volume 是当日累计值，tick 合成 1m 时要 `本tick累计 - 上tick累计`，别直接加。
6. ✅ **trading_day 用 CTP 给的字段** —— 夜盘归属下一交易日，日 K 开盘价=夜盘开盘价（与 vnpy 日线逻辑一致）。
7. ✅ **不处理长假对齐** —— 和所有主流软件一样，只处理周末，节假日靠交易日历表兜底即可。
8. 🔮 **想支持 90 分钟/4 小时等非整除周期** —— 升级到 hxxjava 的"交易时长 traded_t 对齐"，
   放进 `period.lua`，用交易时段字符串驱动。
